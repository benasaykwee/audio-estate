What this is

Every gate PALLBEARER owns passes today, on this machine, freshly run. That is worth saying plainly and first. What follows is not a list of broken tests — it is a list of things that are true about the instrument which no test currently asks about.

Two of them matter. One is a shipping fault in the sound: String Coupling above roughly 30–40% turns the instrument into a self-sustaining drone, and where that line falls depends on how many strings the tuning has. The other is administrative but total: PALLBEARER has never been committed to the repository, so its CI has never run, so the plugin has never been built, so nothing about it being loadable has ever been tested by anything.

The fault — String Coupling is an oscillator above about a third

v0.3 routes each string's bridge output into every other string's delay line. It works. It works too well: the injection sums across the whole set, so the network's loop gain rises with the number of strings, and past a threshold the sympathetic bus stops being a colour and starts being a feedback path that sustains itself.

That flat +4.1 dB is the tell. It is not a loud note — it is an oscillator held still by the soft clipper. The instrument has stopped being struck and started being driven. A player who pulls String Coupling past halfway gets a drone that never stops, and the only thing standing between them and clipping is a saturator doing a job it was not hired for.

Multiply each threshold by (N − 1) and the three numbers collapse into one: 0.42 × 3 = 1.26 · 0.34 × 4 = 1.36 · 0.27 × 5 = 1.35.

That is not a coincidence, it is the diagnosis. bus is the raw sum of every other string's bridge output, so the energy fed back scales with how many strings are on it. The fix is one divisor: normalise the injection by the number of contributing strings. Do that and the threshold sits at couple ≈ 1.3 for every tuning — outside the parameter's own range, which is where an instability threshold belongs. The whole 0–100% of the control becomes usable and, better, means the same thing on a four-string as on a six.

The pitch symptom, which is the same illness

The harness prints 0.184 cents worst tuning error where the README still says 0.085. Nothing regressed — coupling is doing it, and the sweep is monotonic in exactly the way the decay table is:

worst error, cents0.0880.1480.1840.2180.2150.5506.444

Pin couple: 0 and the historical 0.088 cents comes straight back. The section-I test already pins humanize, velBright, buzz and relNoise with a comment explaining exactly why — pin what you are not measuring — and then leaves the one parameter that feeds signal back into the delay line running at its default. The rule was right. It just did not get applied to the newest arrival.

Why nothing caught it

Peak-bounded is not stable. The fuzz harness asserts no NaN, no throw, and peak under 1.6. A self-oscillator held at the soft clipper's ceiling satisfies all three, forever, by construction. It is the most well-behaved signal in the whole corpus and it is the bug.

  • The CPU gate has a coupling_on case, so coupling is exercised — but the gate measures milliseconds. A drone costs the same as a note.
  • The regression baselines are byte-stable, which means they would catch this changing. They cannot catch it being wrong in the first place: a baseline blesses whatever it was first shown.
  • The tuning test is the one gate that did see it. It reported 0.184 instead of 0.085 and its threshold is "under 2 cents", so it shrugged and passed. The number moved by 115% and the assertion never noticed, because the assertion was written around a limit rather than around the previous measurement.
  • The parity gate is at its most convincing here and its least useful: the C++ twin reproduces the oscillation bit-for-bit. Parity proves the two agree, never that either is right.

This one is worth carrying off the project. Any estate gate whose safety net is "the peak stayed under the ceiling" has the same blind spot — RIGOR and NECROPHONE both have feedback paths and both fuzz on peaks. An energy-must-fall assertion is cheap and neither has one.

Not yet in the ground — the administrative fault

PALLBEARER has zero files under version control. Twenty-six files sit untracked, and .github/workflows/pallbearer.yml is untracked alongside them. The estate is seventeen commits ahead of origin/main and none of them contain any of this.

The good news is that everything is ready: the allowlist .gitignore already carries !/PALLBEARER/ and !/.github/workflows/pallbearer.yml, and a dry run stages exactly the right 26 files — sources, gates, the 325 KB parity fixture, both baselines — while correctly leaving build/ behind. Nothing needs deciding. It needs doing.

The consequence is the whole reason "never been BUILT" is still on the list. The macOS job that produces the .component and .vst3 triggers on paths: ['PALLBEARER/**', …]. Files that are not in the repository cannot match a path filter. The build has not failed; it has never been asked.

One caution before anyone types git add. A live .git/index.lock was sitting in the estate root during this audit, minutes old. Sibling sessions run on this folder. Check that the lock is gone and nobody else is mid-write before staging — do not delete the lock to get past it.

The order of work

  1. Normalise the coupling injection
    Divide by the number of contributing strings so loop gain stops scaling with the tuning. JS first, then mirror to PallbearerCore.h — porting is a code review and it goes in that direction. Re-emit parity_expected.h, then re-bless the eleven baselines deliberately and say so in the commit, because they should all move.
  2. Build the gate that would have caught it
    An energy-must-fall assertion: pluck once, sweep couple across its range × every tuning, require the last window to be quieter than the window at one second. It is about fifteen lines and it is the only thing here that stops this class of fault returning. Add a companion that asserts pitch pull stays under a cent across the same sweep.
  3. Pin couple: 0 in the tuning test, and gate the figure not the limit
    Restores the honest 0.088 cents, and moves the assertion from "under 2 cents" to "within a hair of the recorded value" so the next 115% drift is loud instead of silent.
  4. Correct the three prose claims and regenerate THE CARRY
    Cheap, and the 2.6× figure has already leaked. Everything numeric in the README that is not derived should either become derived or become a sentence without a number in it.
  5. Commit, push, and let CI build the thing
    The whole point. Twenty-six files and one workflow. The macOS job then produces the first real .component and .vst3 that have ever existed — after which pluginval, and then Logic, can finally say something no gate on this list can.
  6. Then the standing list, in this order
    Stereo out (both channels are currently identical, and a bass with two pickups has an obvious answer) · oversample the drive stage, watching for the fused multiply-add the Interchange warns about · attack-layer persistence, which needs the audio in the state rather than a file path · a patch library, since nine presets are a literal inside the HTML · and the bespoke editor last, because it is the only item that a compiler-less session cannot verify.

What this audit did not touch

No file was modified. No test was re-blessed. No commit was made. The five probes that produced the tables above ran from /tmp against the core as it stands, and the one re-emit of parity_expected.h was checked byte-for-byte and confirmed unchanged. The instrument is exactly as it was found.
